# Limitations

## Not a filesystem snapshot

The snippet performs two ordinary file reads, not an OS-level snapshot or global lock.

The second-pass hash check detects a source that changed between inventory and archive write when the changed bytes are observed, but it cannot provide transactional consistency across several independently changing files.

For databases or live applications, produce a stable export/snapshot first and bundle that output.

## No symlink support

Symlinks are rejected in v0.1.

This is intentional. The tool does not currently model link target, target provenance, dangling links, external targets, or platform-specific ZIP symlink representation.

## No permissions/ownership preservation

All ZIP members are normalized to regular `0644` files.

Executable bits, source ownership, ACLs, extended attributes and original modification timestamps are not preserved.

Use another archival format/tool when those attributes are part of the artifact contract.

## No compression

v0.1 uses `ZIP_STORED` to keep byte production simple and reproducible.

Large bundles may therefore be substantially larger than a normally compressed ZIP.

## Determinism depends on selected bytes and metadata

Byte-identical output assumes:

- identical source relative paths;
- identical source bytes;
- identical user metadata;
- the same archive algorithm contract.

User-supplied nondeterministic metadata such as a current timestamp naturally makes output differ.

## ZIP implementation compatibility

The implementation normalizes the important member fields it controls, but byte identity across radically different Python/ZIP implementations is not claimed as a formal cross-runtime standard yet.

Tests should compare outputs on the runtimes a project intends to rely on before making a stronger release guarantee.

## Reserved `_bundle/` prefix

Inputs under `_bundle/` cannot currently be archived without renaming/moving them first.

The reservation keeps generated evidence unambiguous.

## SHA-256 proves byte equality, not trust

A manifest hash lets a consumer detect byte changes relative to the recorded manifest. It does not prove that the source file was safe, authentic, reviewed, malware-free, or generated by a trustworthy process.

## No signing

Bundles are not cryptographically signed.

Authenticity/provenance signatures belong in a higher-level release or evidence system.

## No archive encryption

ZIP output is not encrypted. Sensitive artifacts must be protected by external storage/transport controls.

## Memory behavior

Each source file is read fully into memory during inventory and again during archive write.

This keeps hash/write semantics simple but is not suitable for very large individual files without further work. A streaming implementation should preserve the same change-detection contract before replacing this behavior.

## Markdown escaping

The current human summary places paths/metadata in Markdown code spans without a complete escaping grammar for backticks or table-breaking characters. `manifest.json` is the authoritative machine-readable inventory for unusual filenames/metadata.

## No path case-collision model

The selected map is keyed by POSIX-style relative spelling. Repositories moved between case-sensitive and case-insensitive filesystems can have path semantics that the bundle format itself does not resolve.
